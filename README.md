# mayatrail-web

The official website for **MayaTrail** — cloud attack emulation for detection engineers.

**Live at [mayatrail.tech](https://mayatrail.tech)**

## About

This repository contains the source code for the MayaTrail website — a static site (HTML/CSS + a little React) served via nginx in Docker, deployed on AWS. The site code lives in [`site/`](site/).

## The blog

Posts live in [`blog/`](blog/) as Markdown and are rendered to static HTML at
`/blog/` during the Docker build, so the published site stays plain nginx with
no JavaScript and the posts stay indexable.

Write a post as `blog/my-post.md` with YAML front matter:

```yaml
---
title: What a run actually leaves behind
date: 2026-09-10
description: One sentence, used on the index, the meta tag and the RSS feed.
tags: [detection-engineering, aws]
draft: true
---
```

`title` and `date` are required. `draft: true` keeps a post out of the build
until you remove it. The filename becomes the URL: `/blog/my-post/`.

Preview locally:

```bash
pip install -r requirements-blog.txt
python scripts/build_blog.py --drafts --clean
python -m http.server 8000 --directory site
```

`site/blog/` is generated output and is git-ignored — the Markdown is the
source of truth, and the builder stage in the Dockerfile regenerates it on
every deploy.

## The IR playbook page

`site/playbook.html` carries the AMBERSQUID `PLAYBOOK.md` inside an inert
`<script type="text/plain" id="md-source">` block and renders it to static HTML
at build time:

```bash
python scripts/build_playbook.py           # render
python scripts/build_playbook.py --check   # fail if the HTML is stale
```

The Markdown block stays in the page as the source, so the step is idempotent.
The rendered HTML *is* committed (unlike `site/blog/`), because the page is a
normal static page; the Docker builder re-renders it anyway so the two can
never disagree. Update the playbook by editing the Markdown block and
re-running the script.

## The run page

`site/run.html` mounts an interactive simulated emulation run written in JSX
(`site/scripts/run-experience.jsx`). It used to pull React, ReactDOM and
Babel-standalone from unpkg and transpile in the visitor's browser on every
load — about 5.4 MB before anything rendered. The JSX is compiled ahead of time
now, and React is served from this origin:

```bash
npm install
npm run build      # compile the JSX, then vendor React's production UMD builds
```

That writes `site/scripts/run-experience.js` and `site/vendor/*.js`, both
git-ignored and both regenerated by the `jsx` stage in the Dockerfile. Edit the
`.jsx` — it is the source of truth — and re-run `npm run build`. The published
page loads ~196 KB and no third-party script.

## The run page recording

`site/run.html` replays an attack chain from a JSON blob in its `#run-data`
script tag. By default that blob is an authored walkthrough, and the page is
stamped `recorded: false` so the player labels it **ILLUSTRATIVE WALKTHROUGH**
rather than claiming a measured detection rate.

To publish a real run instead, export one from the app repo and commit it:

```bash
# in the app repo
python manage.py export_run_recording <run_id>     --out ../website/mayatrail-web-main/recordings/ambersquid.json

# here
python scripts/build_run.py            # inject it
python scripts/build_run.py --check    # verify without writing
```

Exactly one `recordings/*.json` may exist; two would make the build guess.

**Record only from a dedicated account you are willing to burn.** The exporter
builds its output by allowlist and copies no CloudTrail field by value, but
resource and role names still leak org structure. Three independent checks
guard the boundary — the exporter, `build_run.py`, and a CI step that greps the
committed JSON. A hit in any of them is a bug to fix, not a check to loosen.
