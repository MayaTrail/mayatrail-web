Four steps. No agents. No long-lived keys.

The platform sits behind an STS-only role you grant in a sandbox account. Every resource is tagged. Every action lands in your own CloudTrail.

01 · Connect

STS role, no keys

Grant MayaTrail an assumable role in your sandbox account. The trust policy is two lines. No long-lived credentials ever leave AWS.

02 · Provision

Pulumi sandbox

A tagged stack of intentionally-leaky resources spins up in about 60 seconds. It mirrors a real account in shape, not in data.

03 · Run

Execute a chain

Pick a campaign. Watch the chain land in your CloudTrail. Read which detections fired, and which stayed quiet.

04 · Tear down

One command

The sandbox is destroyed. What you keep is the detection content, the playbook, and the verdict on every rule that should have caught it.

Three states, not two

A rule that didn't alert means one of two very different things. Silent is a tuning problem. No logs is a pipeline problem, and the rule never ran at all. Collapsing them into one number hides the only finding you can act on.

The objections worth answering directly.

The questions we hear most. If yours isn't here, ask: admin@mayatrail.tech.

Will this touch my production account?
No. MayaTrail only acts inside a separate sandbox account you nominate. The trust policy enforces a single sandbox aws:PrincipalAccount condition. Cross-account actions are statically blocked at the SDK layer and at the IAM boundary. Nothing executes against production, ever.
What does a run cost in AWS spend?
A typical chain — roughly 30 seconds of API calls, a small KMS key and a four-object S3 bucket — costs under $0.10. Worst-case scenarios such as a DynamoDB write storm cap at about $1.40. Every run prints a forecast before it executes.
How do I know teardown is real?
Teardown is pulumi destroy with a post-condition: every resource the stack declared must return DescribeX → NotFound. If any survive, the run is flagged incomplete and the teardown log names exactly which resources are still standing. You get logs for both halves.
What if my detections aren't on the grid?
The grid shows the four sources we've benchmarked in beta. Every archived detection is stored raw — the full CloudTrail event, untouched — so you can correlate a run against any stack we don't support yet, on your own schedule. Coverage also exports as an ATT&CK Navigator layer you can load straight into the matrix.
Is this red-team or detection-engineering?
Detection engineering first, red team second. The product is built around "did your stack notice?", not "can you compromise this?" Pacu and others already do the latter well. We're complementary, not a replacement.
Self-host or SaaS?
Both. The emulation core, Pulumi recipes and CLI are open source, and the platform runs as a documented Docker Compose stack. The hosted control plane adds run history, the evidence signer, the detection adapters and a UI. The same chain runs in either mode, and evidence packets are byte-identical.
Which clouds do you support?
AWS. Every chain, every detection bundle and every playbook we ship today targets AWS and nothing else. We would rather cover one cloud thoroughly than claim several thinly.
